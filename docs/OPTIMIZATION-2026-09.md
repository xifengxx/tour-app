# 2026-09 优化变更总结

本文记录本次代码结构、稳定性、性能和测试方面的优化。变更均已在本地完成验证，尚未部署到生产环境。

## 这次解决了什么问题

- 修复异步操作失败后仍更新界面、错误信息不清晰的问题。
- 减少地图脚本对首屏的影响，并增加地图加载失败提示和重试能力。
- 统一静态导览配置，避免首页、数据层各自维护一份列表。
- 拆分 `process-tour` Edge Function，降低入口文件复杂度。
- 将路线站点规划从 AI 输出中独立出来，路线组成由确定性代码控制。
- 使用路由级懒加载降低首屏 JavaScript 负载。
- 将账户菜单从公共导航包中延迟加载。
- 增加错误信息、坐标计算和路线规划的自动化测试。

## 前端变更

### 统一静态导览配置

新增 `src/lib/staticTours.js`，集中维护静态导览的 ID、JSON 文件和首页卡片信息。

以下模块改为使用统一配置：

- `src/pages/Home.jsx`
- `src/hooks/useTourData.js`
- `src/lib/data.js`

这样新增或调整静态导览时只需要修改一个配置源。

### 地图脚本改为按需加载

新增 `src/lib/amap.js`，负责：

- 动态加载高德 JS API。
- 复用同一个加载 Promise，避免重复插入脚本。
- 支持 `VITE_AMAP_KEY` 和 `VITE_AMAP_SECURITY_CODE` 环境变量。
- 加载超时后清理状态，允许用户再次重试。

地图页面和地图搜索弹窗都使用这个加载器。`index.html` 不再直接写入高德脚本和安全码。

### 页面路由懒加载

`src/App.jsx` 使用 `lazy` 和 `Suspense` 按路由加载：

- 首页
- 导览详情
- 导览编辑
- 登录页

构建结果从单个约 672KB 的主 JS 包变为约 441KB 主包，并生成页面级独立 chunk。

导航栏中的账户下拉菜单进一步拆到 `src/components/UserMenu.jsx`，只在登录用户打开导航时加载。`NavBar` chunk 约 34KB，账户菜单和 Radix 下拉菜单依赖单独加载。

### 字体样式异步加载

思源宋体 500/700 两个字重的 `@font-face` 声明（按 unicode-range 分片后约 98 组）原本内联在主样式表中，导致主 CSS 达约 290KB。

现拆分为独立的 `src/fonts.css`，由 `src/main.jsx` 动态导入，Vite 构建为异步加载的独立 chunk：

- 主 CSS：约 290KB → 约 47KB（gzip 约 117KB → 约 9KB），首屏渲染不再被字体声明阻塞。
- 字体 CSS（约 243KB，gzip 约 108KB）与页面渲染并行加载，浏览器仍按 unicode-range 只下载实际用到的字体切片。

### 交互和错误处理

- 新增 `src/lib/errorMessage.js`，统一提取 Supabase 和普通 Error 的可读错误信息。
- 评论、分享、编辑、删除等操作只有在请求成功后才更新界面。
- 修正部分 Hook 依赖和定时器清理。
- 地图增加加载失败状态、超时提示和容器尺寸修复。
- 移动端路线栏增加横向滚动提示。
- Noto Serif SC 字体权重从 500/600/700/900 收敛为 500/700。
- 评论、分享和地图搜索弹窗补充 `role="dialog"`、`aria-modal`、标题关联和输入标签。

## Edge Function 结构变更

`supabase/functions/process-tour/index.ts` 现在主要负责流程编排。辅助职责分布如下：

| 文件                  | 职责                                      |
| --------------------- | ----------------------------------------- |
| `config.ts`           | 环境变量和 Supabase 请求头                |
| `http.ts`             | CORS、JSON 响应、状态写入、批量数据库操作 |
| `ai.ts`               | DeepSeek 请求、重试、截断处理、有界并发   |
| `gaode-search.ts`     | 高德文本搜索和地区景点查询                |
| `gaode-scan.ts`       | 地点名称清洗和周边景点扫描                |
| `gaode-validation.ts` | 高德逆地理编码坐标校验                    |
| `geo.ts`              | `haversineM` 坐标距离计算                 |
| `routes.ts`           | 确定性路线站点规划                        |
| `anchors.ts`          | 景点锚点、子景点和景区归属处理            |

### 行为保持不变的部分

本次模块拆分没有改变以下业务规则：

- 高德城市偏置和裸省名处理。
- 高德限流重试和地点名称匹配规则。
- 子景点过滤、距离去重和锚点合并阈值。
- 1 日、2 日、主题游的路线组成规则。
- DeepSeek 的提示词、模型、重试次数和超时策略。

### 路线规划规则

路线站点组成由 `routes.ts` 确定性计算：

- 1 日精华游：核心景区高重要性地点，最多 20 个。
- 2 日全景游：核心景区加主景区/后山地点，并按距离过滤。
- 主题游：核心热门地点加地区景点聚类代表。
- 文学巡礼线：保留 AI 自由组织能力。

AI 仍然负责路线文案和站内排序，但不能随意增加或删除代码确定的站点集合。

### 2026-09-02 恒山路线与源材料修复

线上复现并修复两个问题：

- 编辑页最终保存时构造的 `source` 缺少 `rawText`，会在用户无感知的情况下覆盖掉源文本；现在加载时同步回填 `sourceText`，最终保存也保留原文。此前已被覆盖的恒山源文本无法从当前数据库记录自动恢复，需要重新粘贴后再触发分析。
- 地区景点合并半径为 60km，但主题游只引用 40km 内代表点，导致应县木塔（约 48km）、华严寺（约 60km）等地点入库后成为无路线引用的“孤岛”。主题游现在使用与地区景点合并一致的 `REGION_RADIUS`。

验证：54 个前端/Edge 单元测试通过，构建和 Deno 类型检查通过；前端已推送 GitHub 自动构建，`process-tour` 已重新部署。恒山最新处理结果包含主题游，并引用应县木塔与华严寺。

### 2026-09-02 恒山核心动线补全

针对“虎风口后直接跳到悬空寺”的路线问题做了三层修复：

- DeepSeek 二次提议之外，新增高德周边文化/自然景点确定性兜底扫描。候选点必须有评分、符合庙殿宫祠或峰岭峡栈道规则，并通过设施/商业过滤、距离去重、逆地理编码区域校验；山地名前缀的“口/岭/峡/栈道”保留一个必选名额，避免虎风口被高评分庙殿挤掉。
- 1 日精华游核心池上限调整为 20：主景点少于 20 个时全部保留，多于 20 个时按重要性截取，避免关键补全点被过早挤出。
- 首层提取新增服务/商业设施过滤，并收紧远距离低重要性点簇恢复规则，避免“服务中心浑源站”和大同市区庙宇混入恒山核心路线。

当前恒山线上数据已修正为：山顶/会仙府 → 天峰岭 → 果老岭 → 虎风口 → 真武庙 → 三清殿 → 悬空寺，并在文案中明确真武庙下方换乘专车、山脚三清殿换乘去悬空寺。高德可稳定返回三清殿坐标（113.725842, 39.651853），新增测试后共 57 个测试通过，Deno 类型检查和前端构建通过。

### 2026-09-03 已知山岳步道知识层

针对 AI 提取结果和地理最近邻排序无法表达“真实步道顺序、换乘点、同名异景点”的问题，新增 `trail-routes.ts` 策展知识层：

- 覆盖泰山、华山、北岳恒山、南岳衡山、嵩山太室山/少室山的经典动线快照；后续可继续补充黄山、张家界等目的地。
- 生成流程在高德定位和核心补全后调用 `injectTrailSeeds`，对已知目的地的关键步道点做最后一层兜底补全；只补有坐标且标记为 required 的站点。
- 一日/主题路线的站内顺序优先使用 `orderStopsByTrail`，只有未命中策展路线时才回退地理最近邻。以恒山为例，新顺序为：北岳恒山 → 三清殿 → 三元宫 → 真武庙 → 虎风口 → 果老岭 → 会仙府 → 天峰岭 → 悬空寺 → 金龙峡 → 翠屏山。
- 文案模型收到已知动线提示，用于写清专车/摆渡车/索道换乘；站点集合和顺序仍由代码控制，AI 不能改站点。
- 运行时不做实时网页抓取。Edge Function 的 60s 预算、目标站反爬和结果稳定性都不适合放在创建导览的关键路径上；策展快照可版本化审查，更新成本也低。

新增 `trail-routes.test.ts` 覆盖恒山步道顺序、关键点补全、同名异景点消歧和未知目的地回退。当前本地共 61 个测试通过。

### 2026-09-03 嵩山重新生成回归修复

线上复现：河南嵩山重新生成后只剩文学巡礼线。处理报告显示 `plans: 2`、`routes: 1`、`corePool: 0`、`mainScenic: ""`。

根因不是路线知识层直接删路线，而是三件旧问题在嵩山样例上叠加：

1. AI 提取到了少林寺、塔林、三皇寨、太室山等真实地点，但没有提取到带“景区/风景名胜区”后缀的伞形锚点；`attachScenicTags` 找不到锚点后把全部地点标记为“独立”，导致 `corePool=0`。
2. 一日精华游的站点集合为空，AI 返回的 slug 又无法匹配地点；空站点路线被过滤，`plans=2` 最终只剩文学巡礼线。
3. 嵩山实际是太室山与少室山两个徒步区。旧知识层只支持“目的地 → 一条步道”，无法把少室山拆到第二个景区池，所以即便匹配到少林寺线路，也不能生成两日分区。

修复：

- 山岳目的地在完全没有景区锚点时，用高德目的地定位点构造核心锚点，避免全部地点落入“独立”。
- `planRoutes` 在核心池为空时回退到全部非地区景点，保证常规一日线不会因空池消失。
- 已知山岳线路支持 `scenicName` 分区；嵩山少室山线路命中少林寺、塔林、三皇寨等地点时，会归入少室山景区池，由 `planRoutes` 生成独立的第二日路线，而不是与太室山混排。
- 文学巡礼线回退站点时也先按已知步道排序，避免按数组顺序产生“少林寺→塔林→中岳庙→峻极峰”这类跨山乱序。

使用嵩山线上落库站点构造回归后：一日线保底有站点，少室山站点进入主景区池，可形成 1 日、2 日和文学巡礼线。当前本地共 63 个测试通过。
