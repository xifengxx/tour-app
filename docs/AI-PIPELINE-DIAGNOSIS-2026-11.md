# 创建导览链路诊断（v99.9 / 2026-11-11）

> 对象：从「用户在 `/create` 填表」到「`process-tour` 写库」的整条链路
> 方法：全量读 `supabase/functions/process-tour/`（生产代码约 4000 行）+ 读库里 `destination_route_knowledge` / `tours.process_report` 实际数据 + 94 条提交历史
> 与 `docs/AI-PIPELINE-REVIEW.md`（2026-08-06，v69）的关系：那份是**单点 bug 清单**（regionMatch 漏 district、deepseek 不重试、截断、卡死），已基本修复；这份是**结构性根因**，解释为什么修完单点后，每来一个新目的地仍要打补丁。

---

## 一、一句话结论

**这条链路的事实来源是「猜」出来的，不是「查」出来的。**

地点清单靠 AI 提名单 + 高德模糊搜索，路线组成靠 `importance` + 地理最近邻 + 字符串标签匹配，两者都用「事后过滤 + 多层兜底」保证不崩。于是：
- 每个新目的地猜错的**方式**不同（漏点 / 多点 / 错点 / 别名不一致 / 解析到行政市）；
- 每次只能针对该目的地补一条规则；
- 规则之间会互相打架，需要再叠一层兜底。

这不是某段代码写坏了，而是**架构把「不可复现的猜测」放在了数据可信度的关键位置**。

---

## 二、链路现状（事实）

### 2.1 五段式流程

| 段 | 位置 | 做了什么 | 事实来源 |
|---|---|---|---|
| ① 入口 | `src/pages/TourEdit.jsx` | 填「目的地 + 地区 + 源文本」，写 `tours`，`status=processing`；`destination.type` **硬编码 `'mountain'`**（:114/:164/:263） | 用户输入，无校验 |
| ② 触发 | `supabase/ai-triggers.sql` | INSERT/UPDATE 触发器 → `pg_net` 调 Edge Function，60s 超时，无重试、无分阶段 | 数据库触发器 |
| ③ 取地点 | `process-tour/index.ts:188-617` | 4 个 AI prompt（核心提取 / 地区景点提议 / 核心补全 / 子景点）+ 高德搜索 + 周边扫描 + 地区知名景点 | **AI 猜 + 高德模糊匹配** |
| ④ 规划 | `routes.ts:261+`（`planRoutes`） | 1 日=核心池按 importance 前 5–8；2 日=核心+主景区；主题游=60km 内簇；顺序=地理最近邻 | **启发式** |
| ⑤ 校验写库 | `route-graph.ts`（1281 行）、`index.ts:960-1121` | 跨区往返、步道回退、时长、容量校验；阻断则 `needs_review` | 规则 + 告警 |

AI 在 ③ 里只负责"提名单"，在 ④ 之后只负责写 `narrative` 文案。**决定"去哪几个点、按什么顺序走"的全是代码与启发式。**

### 2.2 规模与补丁密度（可复核）

- `process-tour/` 目录：**94 次提交**，绝大多数是 `fix(v99.x)` 针对单个目的地事故。
- 生产代码：`index.ts` 1121 行 + `route-graph.ts` 1281 行 + `routes.ts` 508 行 + `trail-routes.ts` 336 行 + 其余 ≈ 4000 行。
- 库里 17 条导览，**每条带 11–22 条 process_report warning**（最高的五台山、三清山测试各 22 条）。
- `destination_route_knowledge` 18 条：**只有 6 条 curated（L3）**——泰山 0.9、华山 0.9、北岳恒山 0.92、南岳衡山 0.9、嵩山 0.92、庐山 0.93；其余 12 条 `auto-research`，置信度 **0.49–0.77**。
- 已经在 `knowledge-tier.ts` 里做过一次"知识分层"（v89），注释原话：*"这是终结'每新增一条导览就要迭代一次规划逻辑'的关键一步"*。分层做了，但 L3 只有 6 个目的地，**其余全部在猜**，所以问题只是被隔离，没有消失。

## 三、四条结构性根因

### 根因 1｜地点清单不可复现

同一目的地跑两次，AI 名单可能不同；高德模糊搜索对同名 POI 的取舍也不稳定。为了让结果"看起来对"，代码在下面这些位置堆了兜底：

| 兜底 | 位置 | 为哪个目的地打的 |
|---|---|---|
| `regionMatch` 支持县级市（district） | `index.ts:89-131` | 嵩山（登封市）→ `locs=0` |
| `pruneFarPoints` 簇感知恢复 | `index.ts:41-74` | 张家界（天门山被 35km 闸误杀） |
| 核心补全 `corePrep` + 周边扫描 | `index.ts:220-363` | 恒山漏真武庙、三清殿 |
| 地区景点并入 + 半径闸 + 别名剔除 | `index.ts:365-451` | 青城山（裸省名"四川"拉进九寨沟） |
| 子景点确定性扫描 + 景区归属 | `index.ts:453-497` | 武陵源（袁家界/十里画廊召回不到） |
| 目的地坐标不可信改用候选质心 | `index.ts:633-649` | 黄山（"黄山"解析到屯溪市区 47km） |
| 锚点必须 ≥40km 内 | `index.ts:471-474` | 五台山（解析到南京） |

这些规则单看都合理，但**它们共同的前提是"上游名单不可信"**。名单可信，它们大多可以删掉。

### 根因 2｜"去哪几个点、怎么排"由启发式决定

`planRoutes` 里 1 日线 = 核心池按 `importance` 取前 N；2 日线 = 核心 + 主景区；顺序 = 地理最近邻。山岳真实动线（红门→中天门→十八盘→南天门）根本不在数据里。

所以每座山都要人肉发现一次锯齿：
- 恒山上下锯齿 → 引入 `injectTrailSeeds` 手写步道（`trail-routes.ts`）；
- 庐山山脚独立景区插进山顶步道 → 引入"高差 ≥800m 且不属于核心片区则降级"（`index.ts:576-610`）；
- 黄山核心池被标签割裂 → 引入"标签池相对地理全集明显残缺则改用地 15km 全集"（`routes.ts:286-304`）。

反证：`trail-routes.ts` 里手写步道的 5 座山（泰/华/恒/衡/嵩），恰好是路线最顺的几条。**说明"知识决定动线"本来就能解决问题，只是知识覆盖太少。**

### 根因 3｜用字符串匹配承担业务语义

- 恒山：AI 叫"恒山"，兜底锚点叫"北岳恒山" → 两套标签永不相交 → 主山点全被推到第二天（`index.ts:509-529` 统一标签变体是补丁）。
- 黄山：`coreScenic` 被 loose 匹配到"温泉景区"1 个点子区 → 1 日线只剩 3 站。
- 景区标签有三个来源（AI 口语名、锚点清洗名、策展 zone 名），三套语义靠 `includes` 对齐。

任何新目的地的命名差异都会击穿某个隐含假设，而击穿方式不可预测。

### 根因 4｜输入质量不前置校验，错误在下游放大

用户地区填「四川」这种裸省名，会连锁触发：AI 提议乐山/九寨沟/峨眉山 → 质心被拉偏 → 60km 闸全杀 → 主题游静默消失。系统在下游用 5 层兜底去补一个**入口就能拒绝的输入**。

同类：`destination.type` 被硬编码 `mountain`，东湖、龟山这类城市水域也被送进山岳动线逻辑。

### 附带：单函数巨流程 + 60s 预算

所有阶段串在一个 Edge Function 里（1121 行），只能靠并发、截断重试、降级抢时间；失败不可从中间阶段续跑，也不能给用户"先看清单再决定"。这是 ③④⑤ 无法拆开验证的根因。

## 四、改造方案（三层，按"先止血再根治"）

### A 层｜入口与校验前置（改动小、见效快）

1. **提交前地名校验**：用高德地理编码确认「目的地 + 地区」能解析出坐标，且坐标逆地理回来落在填写的地区；不符直接拒，并把实际位置告诉用户。
2. **目的地类型必选**：山岳 / 湖泊 / 城市 / 人文 / 古镇，去掉硬编码 `mountain`。
3. **先预演再落库**：新目的地先用本地 dry-run 看「地点清单 + 每条路线的站点与告警」，确认后才提交。

收益：把最贵的失败（跑完 60s 才 error / 或产出一条要人工重排的空壳）提前到提交前。

### B 层｜地点来源从"猜"换成"结构化检索"（中等）

用高德 POI 分类（风景名胜 / 寺庙 / 山峰 / 文物保护）在目的地半径内**直接结构化取点**，按 rating 与类型排序；AI 退到只做命名归一与补漏。

收益：同一目的地两次跑结果可复现；根因 1 里的兜底大部分可以退役。

### C 层｜知识确认闭环（根治，最贵）

研究产出 knowledge 草案（zones / trails / edges + 每站坐标 + 证据 URL + 置信度）→ 创作者确认/改站点顺序 → 标 `creator-confirmed`（L3）→ `process-tour` 退化为**编译器**（坐标校验、去重、按已验证步道装配、生成内容）。

**新目的地不再改代码，只改数据。** 这正是 `route_confirmations` 表的设计意图（自 v83 起因缺 `user_id` 有一条写不进去）。

**顺序**：A → B → C。C 不宜现在直接上，因为底层研究质量不够（0.49 的 auto-research 撑不起「知识决定路线」）。

### 边界

- 现有 14 条已上线导览走双轨：新目的地用新链路，老导览按需重跑。
- `destination.type` 改成必选会改变 research 触发与锚点判定，必须与表单一起改，不能只改表单。
