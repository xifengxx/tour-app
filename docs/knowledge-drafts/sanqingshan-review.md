## 五、结论：C 不是"把现有知识库整理一遍"

**C = 三个来源合并 + 一道确认闸门 + 一个时效字段。**

1. **现有库不够用**：18 条里 12 条是 auto-research，写的全是"索道衔接"。整理它只能得到更整齐的空泛三段式，不会多出一个景点。
2. **必须加联网/官方来源**：环线结构、栈道长度、耗时、住宿、预约制，这些只在官网公告和攻略里。而且**有时效**——玉京峰是 2026-01-01 才开放的，此前的知识写"登玉京峰"就是错的。
3. **确认闸门不可省**：草案的 `source` 我写成 `curated-draft`，故意不写成 `curated`。因为 `knowledge-tier.ts` 只把 `curated / official / manual / creator-confirmed / builtin` 认作 L3，`auto-research` 是 L2。**未经人确认的草案不该直接拿到路线决定权。**
4. **代码目前接不住新字段**：`route-knowledge.ts` 只读 `model.zones / trails / edges`，`availability` 和 `practical` 会被忽略。也就是说，就算现在把这份草案灌进库，玉京峰的预约约束也不会出现在任何地方。这是 C 要补的一条通路（知识字段 → 预演/前台提示）。

## 六、下一步的三个选项

| 选项 | 内容 | 代价 |
|---|---|---|
| ① 只落数据 | 把草案灌进库，`source` 改成 `curated`，让三清山立刻拿到 L3 | 最省，但预约约束仍然不会露出；等于"数据对了，产品没变" |
| ② 数据 + 提示通路 | 草案灌库 + 给 `availability` 补一条读取通道（预演报告与前台"行前须知"各显示一条） | 中等，需要改 Edge Function（当前环境无法部署验证） |
| ③ 先做确认界面 | 先做「草案 → 人审 → 写库」这条链路（对应 `route_confirmations`），再批量铺 12 条 | 最贵，但这是根治"每新增一个导览打一次补丁"的唯一办法 |

我的建议：先做 ② 的一半——**把注释/预约这类"非路线结构"的知识做成前台「行前须知」**，因为它不依赖 Edge Function 部署（读库直出），能在本环境端到端验证；然后再决定要不要投入 ③。

## 七、一个实现约束（实测）

`destination_route_knowledge` 开了 RLS 但没有 grant 策略：

- `service_role` 读 → 200，能拿到数据
- `anon`（前端用）读 → 200，但返回 **`[]`**（空数组，不是报错）

所以前台想直接显示「行前须知」，读这张表是读不到的。三条可选路径：

1. 加一条只暴露 `destination_name + model.availability` 的 RLS 策略（读得到，但 model 是整块 JSONB，会把 zones/trails 一起公开）；
2. 建一张只放公开提示的窄表（如 `destination_notices`），由确认流程写入；
3. 走 Edge Function 中转（需要部署，本环境无法验证）。

按"能不能在本环境端到端验证"排序，② > ① > ③。
